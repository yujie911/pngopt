# PNGOpt —— PNG 图像文件无损压缩工具（可保留透明度）

Windows 命令行工具，对**含透明通道的 PNG** 做逐像素无损压缩。支持单文件、批量文件、文件夹。

作者：Wuhan YuJie

## 快速开始

最简形式——直接把文件路径作为参数：

```bash
pngopt.exe aaa.png          # 压缩 aaa.png，自动输出 aaa_opt.png
```

指定输入输出：

```bash
pngopt.exe -i aaa.png -o min/aaa.min.png
```

批量处理：

```bash
pngopt.exe ./images         # 压缩文件夹内所有 PNG，各自生成 _opt 版本
pngopt.exe a.png b.png      # 空格分隔多个文件
pngopt.exe -i a.png,b.png   # 逗号分隔多个文件
```

查看版本与帮助：

```bash
pngopt.exe -v               # 版本号与作者
pngopt.exe -help            # 完整帮助
```

### 命令行选项

| 选项 | 说明 |
|---|---|
| `<路径>` | 位置参数，直接指定输入文件/文件夹（可多个，空格分隔） |
| `-i <路径>` | 输入路径（文件 / 文件夹 / 逗号分隔的多个路径） |
| `-o <路径>` | 输出路径（单文件时为输出文件，多文件时为输出目录） |
| `-v` | 显示版本号与作者 |
| `-verbose` | 详细模式：显示每个候选过滤策略的压缩体积 |
| `-help` | 显示帮助信息 |

### 输出规则

| 场景 | 输出 |
|---|---|
| 未指定 `-o` | 在源文件旁生成 `<原名>_opt.png` |
| 单文件 + `-o 文件` | 输出到指定文件 |
| 多文件 + `-o 目录` | 输出到该目录，文件名仍带 `_opt` |

> 批量处理时自动跳过 `_opt` 结尾的文件，避免反复压缩自己的产物。

## 压缩算法

三层流水线，每层都做了"实测验证 → 只保留最优方案"的取舍。

### 第一层：色彩模型无损降级

很多 PNG 携带了用不到的通道，这是最大的一块浪费空间。

| 降级路径 | 条件 | 典型收益 |
|---|---|---|
| RGBA → 索引色 | 颜色数 ≤ 256 | 极大（UI 图标常见 70%+） |
| RGBA → RGB | 全部不透明 | ~25% |
| RGB → 灰度 | R=G=B | ~66% |
| RGBA → 灰度+tRNS | 单一透明灰阶 | 省一个通道 |
| 16bit → 8bit | 高低位一致 | ~50% |
| 灰度 → 1/2/4bit | 值分布可整除 | 视数据而定 |

关键在于**必须可证明无损**：像素先规范化到 16 位 RGBA，
每个降级方案都要检查"能否用目标位深精确还原"，只有通过的才被采纳。

**实现要点**：色彩模型不是"枚举后逐个压缩评估"，而是**一次遍历统计特征后直接定案**。
旧实现要对每个候选（常有 6+ 个）跑完整的过滤策略评估，这部分是主要的性能浪费。

### 第二层：过滤策略搜索

PNG 在压缩前对每条扫描线施加 5 种预测过滤器之一（None/Sub/Up/Average/Paeth），
把相邻像素的差值写进文件以提升可压缩性。选哪个是逐行独立的组合优化问题。

实现的 8 种策略：

- **固定过滤器 0~4** —— 整图统一使用一种
- **逐行最小和** —— PNG 规范的经典启发式
- **逐行最小熵** —— Shannon 熵
- **逐行最少 bigram** —— 相邻字节对多样性

> 过滤器只做预处理，不改变像素数据，因此严格无损。

**实现要点**：三种逐行策略共享同一次过滤计算（5 种过滤器结果对所有评分函数通用），
把过滤阶段的计算量降到 1/3。

### 第三层：DEFLATE 熵搜索（Zopfli）

Google 的 Zopfli 用迭代式熵搜索穷尽 Huffman 树构造与块分割的自由度，
在标准 DEFLATE 格式下找到更小的编码。

**实测对比**（同一份 480KB 像素数据）：

| 后端 | 体积 | 耗时 |
|---|---|---|
| 标准库 zlib level-9 | 444,880 字节 | 9ms |
| **Zopfli** | **411,133 字节** | 872ms |

Zopfli 小 **7.59%**，与文献记载的 3~8% 吻合。输出仍是标准 DEFLATE 流，任何解码器都能读。

## 性能设计

### 瓶颈定位

对 256×256 图标的分阶段计时：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 解码 + 规范化 + 色彩模型 | 6ms | 0.3% |
| 过滤策略生成 | 38ms | 2% |
| 快速评估排序 | 136ms | 7% |
| **Zopfli 压缩** | **1694ms** | **90%** |

Zopfli 是唯一的瓶颈，因此所有优化都围绕它展开。

### 关键实测数据与决策

**1. Zopfli 迭代次数：it=2 即收敛**

| 迭代 | 体积 | 耗时 |
|---|---|---|
| it=1 | 7603 | 1599ms |
| **it=2** | **7547** | **1790ms** |
| it=5 | 7527 | 2376ms |
| it=15 | 7525 | 4261ms |

it=15 与 it=5 体积仅差 2 字节却慢 1.8 倍。**取 it=2**。

**2. 快速评估的可靠性：与 Zopfli 最优差距平均 0.02%**

对 9 个测试图，快速 DEFLATE 评估排名第 1 的策略，与 Zopfli 压缩后最优策略
在 8 个图上完全一致，最差的一个（照片图）只差 0.18%。

**因此只跑 1 次 Zopfli**，而非对所有候选都跑——Zopfli 计算量降到 1/8，
体积损失 <0.2%。

**3. Zopfli 恒定慢 90 倍**

| 数据量 | zlib-9 | Zopfli | 倍数 | Zopfli 体积优势 |
|---|---|---|---|---|
| 256 KB | 19ms | 1.71s | 90× | 8.20% |
| 1 MB | 78ms | 7.12s | 92× | 8.44% |
| 4 MB | 330ms | 30.06s | 91× | 8.58% |

比例不随规模变化，说明两者都线性扩展。因此**按数据量自适应**：

- 过滤后数据 ≤ 512KB → 用 Zopfli（保最优体积）
- 超过 → 用 zlib level-9（避免为 8% 体积付出 90 倍时间）

**4. 大文件路径：每个候选只压缩一次**

大文件时"快速评估 + 最终压缩"会重复压缩同一份数据。改为：
精简策略集（5 个，实测与全量 8 策略排序结果完全一致）→ 并行做终局压缩取最小。
2048×2048 图标：**11.0s → 4.0s，体积完全相同**。

### 并发模型

两层并发叠加：

- **文件级**：worker 池处理多个文件，并发度为 CPU 核数的一半
  （给文件内的策略并行留出余量）
- **文件内**：8 种过滤策略的数据流并行生成

单文件 256×256 图标：4.44s → **1.89s**。
批量 17 个文件：**2.16s，平均 387ms/文件**。

### 最终性能

| 场景 | 耗时 | 压缩率 |
|---|---|---|
| 256×256 RGBA 图标 | 1.89s | 18.53% |
| 400×300 照片 | 1.77s | 65.85% |
| 200×200 色块 | 46ms | 72.22% |
| 300×150 灰度 | 34ms | 76.83% |
| 2048×2048 图标 | 4.25s | 29.55% |
| 批量 17 文件 | 2.16s | 50.11% |
