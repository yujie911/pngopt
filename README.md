# pngopt —— PNG 无损压缩工具（保留透明度）

Windows 命令行工具，对**含透明通道的 PNG** 做逐像素无损压缩。支持单文件、批量文件、文件夹。

**版本 1.0.2** · 作者：Wuhan YuJie

## 快速开始

最简形式——直接把文件路径作为参数：

```bash
pngopt.exe aaa.png          # 压缩 aaa.png，自动输出 aaa_opt.png
```

指定输入输出：

```bash
pngopt.exe -i aaa.png -o min/aaa.min.png
```

批量处理：

```bash
pngopt.exe ./images         # 压缩文件夹内所有 PNG，各自生成 _opt 版本
pngopt.exe a.png b.png      # 空格分隔多个文件
pngopt.exe -i a.png,b.png   # 逗号分隔多个文件
```

查看版本与帮助：

```bash
pngopt.exe -v               # 版本号与作者
pngopt.exe -help            # 完整帮助
```

### 命令行选项

| 选项 | 说明 |
|---|---|
| `<路径>` | 位置参数，直接指定输入文件/文件夹（可多个，空格分隔） |
| `-i <路径>` | 输入路径（文件 / 文件夹 / 逗号分隔的多个路径） |
| `-o <路径>` | 输出路径（单文件时为输出文件，多文件时为输出目录） |
| `-v` | 显示版本号与作者 |
| `-verbose` | 详细模式：显示每个候选过滤策略的压缩体积 |
| `-help` | 显示帮助信息 |

### 输出规则

| 场景 | 输出 |
|---|---|
| 未指定 `-o` | 在源文件旁生成 `<原名>_opt.png` |
| 单文件 + `-o 文件` | 输出到指定文件 |
| 多文件 + `-o 目录` | 输出到该目录，文件名仍带 `_opt` |

> 批量处理时自动跳过 `_opt` 结尾的文件，避免反复压缩自己的产物。

## 压缩算法

三层流水线，每层都做了"实测验证 → 只保留最优方案"的取舍。

### 第一层：色彩模型无损降级

很多 PNG 携带了用不到的通道，这是最大的一块浪费空间。

| 降级路径 | 条件 | 典型收益 |
|---|---|---|
| RGBA → 索引色 | 颜色数 ≤ 256 | 极大（UI 图标常见 70%+） |
| RGBA → RGB | 全部不透明 | ~25% |
| RGB → 灰度 | R=G=B | ~66% |
| RGBA → 灰度+tRNS | 单一透明灰阶 | 省一个通道 |
| 16bit → 8bit | 高低位一致 | ~50% |
| 灰度 → 1/2/4bit | 值分布可整除 | 视数据而定 |

关键在于**必须可证明无损**：像素先规范化到 16 位 RGBA，
每个降级方案都要检查"能否用目标位深精确还原"，只有通过的才被采纳。

**实现要点**：色彩模型不是"枚举后逐个压缩评估"，而是**一次遍历统计特征后直接定案**。
旧实现要对每个候选（常有 6+ 个）跑完整的过滤策略评估，这部分是主要的性能浪费。

### 第二层：过滤策略搜索

PNG 在压缩前对每条扫描线施加 5 种预测过滤器之一（None/Sub/Up/Average/Paeth），
把相邻像素的差值写进文件以提升可压缩性。选哪个是逐行独立的组合优化问题。

实现的 8 种策略：

- **固定过滤器 0~4** —— 整图统一使用一种
- **逐行最小和** —— PNG 规范的经典启发式
- **逐行最小熵** —— Shannon 熵
- **逐行最少 bigram** —— 相邻字节对多样性

> 过滤器只做预处理，不改变像素数据，因此严格无损。

**实现要点**：三种逐行策略共享同一次过滤计算（5 种过滤器结果对所有评分函数通用），
把过滤阶段的计算量降到 1/3。

### 第三层：DEFLATE 熵搜索（Zopfli）

Google 的 Zopfli 用迭代式熵搜索穷尽 Huffman 树构造与块分割的自由度，
在标准 DEFLATE 格式下找到更小的编码。

**实测对比**（同一份 480KB 像素数据）：

| 后端 | 体积 | 耗时 |
|---|---|---|
| 标准库 zlib level-9 | 444,880 字节 | 9ms |
| **Zopfli** | **411,133 字节** | 872ms |

Zopfli 小 **7.59%**，与文献记载的 3~8% 吻合。输出仍是标准 DEFLATE 流，任何解码器都能读。

## 性能设计

### 瓶颈定位

对 256×256 图标的分阶段计时：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 解码 + 规范化 + 色彩模型 | 6ms | 0.3% |
| 过滤策略生成 | 38ms | 2% |
| 快速评估排序 | 136ms | 7% |
| **Zopfli 压缩** | **1694ms** | **90%** |

Zopfli 是唯一的瓶颈，因此所有优化都围绕它展开。

### 关键实测数据与决策

**1. Zopfli 迭代次数：it=2 即收敛**

| 迭代 | 体积 | 耗时 |
|---|---|---|
| it=1 | 7603 | 1599ms |
| **it=2** | **7547** | **1790ms** |
| it=5 | 7527 | 2376ms |
| it=15 | 7525 | 4261ms |

it=15 与 it=5 体积仅差 2 字节却慢 1.8 倍。**取 it=2**。

**2. 快速评估的可靠性：与 Zopfli 最优差距平均 0.02%**

对 9 个测试图，快速 DEFLATE 评估排名第 1 的策略，与 Zopfli 压缩后最优策略
在 8 个图上完全一致，最差的一个（照片图）只差 0.18%。

**因此只跑 1 次 Zopfli**，而非对所有候选都跑——Zopfli 计算量降到 1/8，
体积损失 <0.2%。

**3. Zopfli 恒定慢 90 倍**

| 数据量 | zlib-9 | Zopfli | 倍数 | Zopfli 体积优势 |
|---|---|---|---|---|
| 256 KB | 19ms | 1.71s | 90× | 8.20% |
| 1 MB | 78ms | 7.12s | 92× | 8.44% |
| 4 MB | 330ms | 30.06s | 91× | 8.58% |

比例不随规模变化，说明两者都线性扩展。因此**按数据量自适应**：

- 过滤后数据 ≤ 512KB → 用 Zopfli（保最优体积）
- 超过 → 用 zlib level-9（避免为 8% 体积付出 90 倍时间）

**4. 大文件路径：每个候选只压缩一次**

大文件时"快速评估 + 最终压缩"会重复压缩同一份数据。改为：
精简策略集（5 个，实测与全量 8 策略排序结果完全一致）→ 并行做终局压缩取最小。
2048×2048 图标：**11.0s → 4.0s，体积完全相同**。

### 并发模型

两层并发叠加：

- **文件级**：worker 池处理多个文件，并发度为 CPU 核数的一半
  （给文件内的策略并行留出余量）
- **文件内**：8 种过滤策略的数据流并行生成

单文件 256×256 图标：4.44s → **1.89s**。
批量 17 个文件：**2.16s，平均 387ms/文件**。

### 最终性能

| 场景 | 耗时 | 压缩率 |
|---|---|---|
| 256×256 RGBA 图标 | 1.89s | 18.53% |
| 400×300 照片 | 1.77s | 65.85% |
| 200×200 色块 | 46ms | 72.22% |
| 300×150 灰度 | 34ms | 76.83% |
| 2048×2048 图标 | 4.25s | 29.55% |
| 批量 17 文件 | 2.16s | 50.11% |

## 进度显示

### 实现要点

进度条由**后台定时器驱动**（100ms 一次），而不是靠事件触发。
这一点很关键：压缩耗时的 90% 集中在 Zopfli 单个阶段内部，
若只在阶段切换时刷新，进度条会长时间静止，看上去像"卡死"。

阶段内没有可用的进度回调（Zopfli 不提供），因此**不做时间插值**——
凭时间臆造百分比会误导用户。阶段内的"仍在工作"由两个信号表达：

- **旋转指示器** `| / - \` 每 100ms 换一帧
- **实时耗时** 持续递增

百分比只在阶段完成时按实测耗时权重跳变（解码 2% → 分析 4% → 策略 9% → Zopfli 97% → 校验 100%）。

多文件模式下，总进度按「已完成文件数 + 进行中文件的阶段进度」加权计算，
批次处理过程中同样平滑推进，而不是等文件完成才跳变。

### 终端兼容性

Windows 上 Go 不会自动开启控制台的 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`，
导致 `\033[K`（清除行）等序列在传统 cmd.exe 中被当作普通字符打印，
进度条表现为乱码。程序启动时通过 `SetConsoleMode` 主动开启该模式。

同时做终端检测，输出被重定向到文件或管道时自动降级：
不输出任何 ANSI 序列，只打印纯文本阶段日志，保证日志文件干净。

### 自测

`progress_test.go` 覆盖 7 项回归测试：

| 测试 | 验证内容 |

| TestProgressRefresh | 长阶段内持续重绘（1 秒 ≥ 5 次） |
| TestProgressStageJump | 阶段推进时进度单调不减、阶段内稳定 |
| TestSpinnerRotates | 指示器帧完整 |
| TestNonInteractiveNoANSI | 非终端环境不输出 ANSI 序列 |
| TestEnableANSI | 控制台检测与 ANSI 启用逻辑 |
| TestStageTimingMatchesWork | 阶段上报与实际耗时对应 |
| TestMultiProgressSmooth | 多文件总进度平滑推进 |

## 二进制体积

实测各部分占比：

| 部分 | 体积 |
|---|---|
| Go 运行时（不可压缩） | 2.46 MB |
| zopfli 库净贡献 | 140 KB |
| 本项目业务代码 | 极小 |

**关键结论**：体积的大头是 Go 运行时，不是压缩方案。
删掉多余的压缩算法省不下多少（算法代码只有几 KB），
真正有效的是剥离符号表与调试信息：

```bash
go build -ldflags="-s -w" -o pngopt.exe .
```

**3.29 MB → 2.29 MB（省 1.04 MB，31.7%）**

另外，重构后不再需要 `klauspost/compress` 依赖（改用标准库 `compress/zlib`），
`go mod tidy` 已自动移除，当前唯一外部依赖是 `github.com/foobaz/go-zopfli`。

## 正确性保证

程序在写完输出后**必定执行双重校验**，任一环节失败即报错退出（不会留下错误的输出文件）：

1. **自研解码器**重新解析输出，逐像素与原图比对
2. **Go 标准库 `image/png`** 独立解析输出并逐像素比对

第 2 步不可省略——编码器与解码器若共享同一套错误约定（例如 tRNS 字节语义写错），
第 1 步会"自己验证自己"而漏过问题。开发过程中正是标准库交叉校验
捕获了一个会导致半透明像素变不透明的 tRNS 缺陷。

### 已验证的边界情况

| 类型 | 覆盖内容 |
|---|---|
| 色彩类型 | 灰度 / 真彩 / 索引色 / 灰度+Alpha / RGBA |
| 位深 | 1 / 2 / 4 / 8 / 16 bit |
| 透明度 | 全透明 / 半透明 / tRNS 单色透明 / 调色板 tRNS 数组 |
| 其他 | Adam7 隔行、1×1 极小图、纯色图、元数据块保留与丢弃、bKGD/sBIT 色彩类型兼容性 |

全部 17 项测试用标准库交叉校验通过（测试用例为开发期产物，未随交付保留）。

## 构建

推荐用构建脚本，它会在编译前**自动把版本号尾数 +1**：

```bash
cd pngopt
./build.sh            # 1.0.4 → 1.0.5，编译并校验版本号
./build.sh --no-bump  # 不递增版本号（调试用）
```

Windows 下也可以：

```cmd
cd pngopt
build.cmd
```

脚本做三件事：

1. 从 `cli.go` 读出当前版本号，尾数 +1
2. 把新版本号写回源码，并用 `-ldflags -X` 注入二进制
3. 编译后执行 `pngopt.exe -v` 校验二进制里的版本号确实生效

版本号同时写在源码与二进制中，二者始终一致——不会出现"源码改了但发出去的 exe 还是旧版本"的情况。

手工编译（不递增版本号）：

```bash
go build -trimpath -ldflags="-s -w" -o pngopt.exe .
```

依赖：`github.com/foobaz/go-zopfli`（Google Zopfli 的纯 Go 移植，含 zlib 容器）。

无需 cgo，单文件可执行文件，直接分发即可。

## 版本信息

版本号与作者定义在 `cli.go` 顶部：

```go
var (
	version = "1.0.4"
	author  = "Wuhan YuJie"
)
```

`pngopt.exe -v` 即显示这两项。`version` 是变量而非常量，构建脚本可通过
`-ldflags "-X main.version=x.y.z"` 覆盖它。

**版本号约定**：涉及程序、需要重新编译时，每次编译前默认把版本号尾数 +1
（主版本号/次版本号仅在明确要求时才动）。`build.sh` 已把这条约定自动化。
